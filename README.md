# Retail Demand Forecasting & Inventory Optimization Dashboard

A planning dashboard that turns two years of store-level transaction history into
a **forecast you can audit** and an **inventory policy you can act on**.

Every number on the board is either backtested out of sample or derived live in
the browser from an explicit formula — nothing is a static mock-up.

## What it does

**Forecasting (offline, Python)**

* Builds a 6-store × 15-SKU daily demand panel (735 days, 66k rows) with weekly
  and annual seasonality, price elasticity, promotion lifts, holiday effects and
  negative-binomial overdispersion.
* Fits a ridge regression per store × SKU on features that are *known in
  advance* — day of week, Fourier annual terms, trend, log price ratio,
  promotion flag, holiday flag, promo × price interaction — in `log1p` space with
  a log-normal retransformation. Because every feature is known ahead of time,
  this is a **direct multi-horizon** forecaster: no recursion, no compounding
  error, and each coefficient is readable by a planner.
* Validates with a **rolling-origin backtest** (3 folds × 28 days) against a
  seasonal-naive benchmark (mean of the last four same-weekday observations).
* Derives 80% prediction intervals from horizon-specific backtest residuals,
  not from in-sample fit.

| WAPE | **0.309** | 0.399 |

— a 22.6% error reduction over the benchmark.

**Inventory optimization (live, TypeScript)**

Policy maths runs in the browser so the whole network recomputes on every slider
move. The model is a continuous-review (s, Q) system with a periodic-review
order-up-to overlay:

```
safety stock   SS = z(α) · σ_d · √(L + R)
reorder point   s = μ_d · L + SS
order quantity  Q = EOQ = √(2 D S / H),   H = holding_rate · unit_cost
order-up-to     S = μ_d · (L + R) + SS
fill rate       = 1 − σ_d √(L+R) · G(z) / Q
```

`σ_d` is the **out-of-sample forecast error**, not the historical demand
standard deviation — using the latter is the most common way safety stock ends
up wrong. Fill rate comes from the unit normal loss function `G(z)` rather than
being assumed equal to the cycle service level; the gap between those two is
exactly where over-stocking hides.

**What the dashboard shows**

* Network demand: 120 days of actuals and a 28-day forecast with an 80% band,
  aggregated by adding *variances* across independent series, not interval widths.
* Service level vs annual cost: holding, shortage and ordering cost decomposed
  across 31 service levels, with the cost-minimising point marked. It is rarely 99%.
* Out-of-sample accuracy by category against the naive benchmark.
* ABC revenue Pareto (80/15/5) driving class-specific review policy.
* Exception queue: expedite / reorder / overstock lines ranked by revenue at risk,
  each with a suggested order quantity rounded to the supplier case pack.
* A sortable policy table for all 90 store × SKU lines.

Filters (store, category, ABC class, horizon, service level, stockout penalty)
re-derive every KPI, chart and row.

## Running it

```bash
npm install
npm run pipeline    # regenerate public/dashboard.json (needs numpy + pandas)
npm run dev         # http://localhost:5173
npm run build       # static bundle in dist/
```

The pipeline takes under a second and writes a single ~160 KB JSON payload that
the dashboard fetches at load. Re-running the pipeline is enough to refresh the
site — no rebuild required.

Python dependencies: `pip install -r pipeline/requirements.txt`.

## Layout

```
pipeline/
  generate_data.py   synthetic demand panel with a documented DGP
  forecast.py        design matrix, ridge fit, backtest, intervals
  run_pipeline.py    orchestration -> public/dashboard.json
src/
  lib/inventory.ts   normInv, unit normal loss, (s,Q) policy, rollups, ABC
  lib/types.ts       payload contract shared with the pipeline
  components/        dashboard panels (Recharts)
```

## Notes on the data

The transaction history is synthetic and generated by `pipeline/generate_data.py`
with a fixed seed, so results are reproducible. The data-generating process is
written out explicitly in that file — the forecasting model is solving a problem
whose signal is known and checkable, which is what makes the accuracy comparison
above meaningful rather than decorative.

Current on-hand positions are randomised within a plausible range so the
exception queue has real work in it; swap that block for a feed from your WMS to
run this against live inventory.
